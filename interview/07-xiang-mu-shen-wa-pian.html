Q01 · "我做过一个联网深度研究 Agent"——怎么经得起深挖？

难度：★★★★ ｜ 频率：极高（简历写了必被问）｜ 对应课件：agent核心/09

面试官：简历上写你做过 DeepResearch Agent。介绍一下：它解决什么问题？架构是什么？

第 1 层追问：30 秒版本介绍

先把项目说清楚。

参考回答（骨架）："我做了一个给定开放问题、联网查证、产出带引用答案的研究 Agent。比如问'对比 A 和 B 两个技术选型'，它会自主多轮搜索、阅读网页、交叉验证，最后给出每条结论都带来源链接的报告。为什么用 Agent 而不是固定流程：研究任务的步骤写不死——搜几轮、读哪些页取决于中间结果，必须让模型运行时决策。核心架构三件套：两个正交小工具（web_search + read_webpage，后者返回清洗截断后的正文）、ReAct 主循环（反复调用模型直到它不再请求工具）、四道终止闸门（自然终止/轮次上限/token 预算/重复检测）。"——先说问题、再说选型理由、后给结构，30 秒内完成。

第 2 层追问：技术决策深挖

你说"两个小工具"，为什么不做一个"搜索并总结"的复合工具？

参考回答（决策逻辑）："试过比较后选的拆分方案，理由是三条。一，参数越少填对率越高：模型是按工具描述的概率系统，复合工具参数多、分支多，填错率随复杂度上升。二，正交组合出涌现策略：两个工具职责不重叠，模型在运行时自己组合出'并行发多个搜索 → 筛选 URL 精读 → 对比多方信息再下结论'的策略——这个策略我没有写进代码，是模型自己发展出来的，这也是我做这个项目最惊讶的发现。三，独立可测：两个工具单独 mock 测试，故障定位快。"——展示比较过方案 + 有真实发现。

第 3 层追问：最难的 bug

开发过程中印象最深的问题是什么？

参考回答（真实踩坑）："死循环。早期版本 while True 唯一出口是模型自己停止要工具——某天它开始用完全相同的参数反复调 web_search，我盯着 token 一秒一秒烧。加轮次上限只是止血，真正解决靠两层：重复检测闸门（连续 N 次调用哈希相同就强制中断）+ 纠偏提示（中断时往上下文注入'你已连续 3 次用相同查询，请更换关键词或放弃该方向'——一次纠偏大多数循环就解开了）。后来复盘根因：提示词里没给模型'承认失败'的出口，模型不知道'放弃也是合法选项'。"——现象、止血、根治、根因四段式，这是排查型回答的满分结构。

第 4 层追问：量化与局限

效果怎么样？这个项目还有什么不足？

参考回答（量化 + 诚实）："我建了个 20 题的测试集跑过基线：任务成功率约 7 成（多次运行取平均——概率系统必须多次跑，单次结果没有意义），平均 6.8 轮工具循环，平均 token 消耗约 X 万（这个数必须换成你的真实测量）。失败案例聚类后主要是两类：搜索结果质量差（占一半）和多轮后上下文漂移。明确的局限：没有长期记忆（跨会话不记得研究过什么）、工具返回没做更狠的压缩（长调研任务后期上下文压力大）、没有并行工具执行（执行侧是串行 await，还有提速空间）——这三个也正是我下一版的 roadmap。"——主动说局限是资深信号：知道边界的人才会被信任去碰生产。

考察意图与踩坑点

  • 考察意图：验证项目真实性。所有"面试官"的追问都在执行同一个判别：你是照着教程敲的，还是带着工程判断在做。
  • 踩坑点：介绍项目从"我先用 LangChain 装了个包"开始讲流程（没人关心你的步骤）；量化数据说不出（没测过就说没测过，编数字被追问立刻塌）；被问局限时说"没有了"（等于宣告没深入做过）。
  • 一句话总结：问题→选型理由→结构→真实踩坑→自己的数字→主动的局限——六个格子填满，这个项目就是你的。

Q02 · "多智能体并行调研系统"——asyncio 实战项目怎么讲？

难度：★★★★ ｜ 频率：高 ｜ 对应课件：Python与数据实践/21-asyncio实战

面试官：你简历上还有个"异步多 Agent 调研系统"，产出数据库选型对比报告的那个。讲讲它和上一个 Agent 的区别。

第 1 层追问：项目定位

这个项目的技术重心是什么？

参考回答："技术重心从单 Agent 行为设计换成了并发编排——这是个 asyncio + LLM 的工程练手：给定'对比 Python 项目常用的数据库'这类主题，系统拆分出多个调研方向，并行派出多个 field agent 各自调研（联网查证 + LLM 分析），全部回收后汇总成结构化报告。和单 Agent 项目的本质差异：挑战从'让模型行为可靠'变成'让 IO 并发正确'——十几个协程的调度、限流、超时、结果聚合。"——两句话定位清楚考察点换了赛道，引导面试官往你的强项问。

第 2 层追问：并发设计深挖

具体怎么编排的？并发数怎么控制？

参考回答："结构上是conductor（编排协程）+ 若干 field_agent（调研协程）+ splitter/digest 等纯函数模块。三个关键并发设计：一，Semaphore 全局限流——asyncio.Semaphore 限制同时在飞的 LLM 请求数（上游有速率限制，不加闸门就是被 429 教育的结局）。二，gather 保序聚合——并发发出后结果按序回收，调研结论和方向标签的对应关系不乱（顺序乱了，报告段落就张冠李戴）。三，单分支超时不拖垮整体——每路调研有自己的超时，超时标记该分支 failed，其他分支继续，汇总时对缺失部分明示'未覆盖'。"——限流、保序、故障隔离，并发三要素一个不少。

第 3 层追问：踩坑深挖

并发这块你踩过什么坑？

参考回答（真实陷阱）："两个经典坑。坑一：阻塞调用混进事件循环——早期 LLM 客户端用了同步 SDK，第一个请求发出整个 loop 就冻住，所有协程集体'并发'变串行还互相卡；换成异步客户端 + 后来养成了'进 loop 的东西全部 async 化'的习惯。坑二：异常吞没——gather 默认一个协程抛异常整组炸，调研任务里一个网络抖动就把整体报告带崩；改成 return_exceptions=True 逐路收集结果，失败分支进降级路径。这两个坑让我真正理解了'asyncio 的并发安全靠纪律不靠语言'——语言给了你协程，坑要自己绕。"——细节具体到 API 名，可信度自然拉满。

第 4 层追问：追问性价比

这个项目里 LLM 调用和普通 IO 有什么不同？异步收益怎么量化？

参考回答："三点不同让并发收益放大。一，单次延迟大——LLM 请求秒级起步（普通 HTTP 毫秒级），串行 10 个方向 = 用户等一分钟，并发后总时长≈最长单路。二，成本维度——并发不省 token（钱只和调用量相关），省的是时间；要省钱得靠砍轮次和压缩上下文，这两个正交目标我一开始混为一谈后来才分清。三，稳定性维度——LLM 服务的超时率和限流比普通服务高，重试 + 退避策略必须有。量化：同样 10 个调研方向，串行版 X 分钟，并发版 Y 分钟（换成你的实测数字），提升 Z 倍但 token 成本不变——这个'免费的速度'就是 asyncio 在 LLM 应用里的核心价值。"

考察意图与踩坑点

  • 考察意图：这题同时考异步编程功底和"LLM IO 的特殊性"理解——是 Python 工程课和 Agent 课的交叉点，答好即证明课程体系在你身上融会了。
  • 踩坑点：说不出 Semaphore/gather 保序的具体用法（背概念没实操）；阻塞调用的坑没踩过也没听说过；把"省时间"和"省钱"混着说。
  • 一句话总结：定位讲清赛道切换（行为→并发）；限流、保序、故障隔离三件套；阻塞混入 loop 和 gather 吞异常两大坑；量化"免费的速度"。

Q03 · "知识库问答（RAG）项目"——别让最常见的项目变成最平庸的介绍

难度：★★★ ｜ 频率：极高（人人简历都有 RAG，差异化全靠深挖）｜ 对应课件：LangChain指南/06-08

面试官：RAG 项目大家都有。你这个和别人的有什么不一样？

第 1 层追问：标准介绍 + 差异化锚点

30 秒介绍，但要有记忆点。

参考回答："我做的是书屋知识库问答：店员的经营笔记、书目 CSV、活动通知入库，用户提问时检索相关片段、模型只依据材料作答、答案必须能溯源到具体文档。流程上是标准 RAG（加载→结构化切割→嵌入→向量库→检索→生成），但我可以讲清楚每一环为什么这么设计——比如切割：Markdown 笔记按标题层级切、CSV 一行一 Document、纯文本才退到字符滑动窗口；再比如防幻觉：提示词'只依据材料回答'只是第一道闸，引用校验（每个引用必须真实存在于检索结果里）才是硬闸。"——差异化锚点 = "每一环都有决策理由"，这句话本身就是和别人拉开差距的宣言。

第 2 层追问：检索质量深挖

用户的提问和笔记的表述对不上，检索不出来，你怎么办？

参考回答："这是我迭代最多的环节，分了三步走。第一步参数层：k + score_threshold + metadata filter 三件套调对——特别是 threshold，宁可拒答不给错料。第二步多样性：开 MMR（fetch_k 取大池、lambda_mult 平衡相关性和多样性），解决 top-k 全是同一段的近亲问题。第三步查询改写：这是收益最大的一刀——口语提问和文档表述的鸿沟，用多查询检索补：让 LLM 把'几点关门'改写成'营业时间/闭店时间/开放时段'多个问法分别检索再合并。如果还不行，往上还有混合检索（BM25 抓精确词）和重排没上，是因为我的数据规模用不上——每一步优化都要有'当前问题的证据'，不是把菜单全点一遍。"——最后半句是防"技术清单堆砌"的关键：说清楚为什么没做和做了什么同样加分。

第 3 层追问：评估深挖

你说"迭代最多"，怎么知道迭代有效？

参考回答："建了个小评测集分两段测。检索段：30 个问题标注了出处块，测命中率和 MRR——参数调整前后跑对比（比如 MMR 开启后命中率从 X% 到 Y%，换成你的实测数）。生成段：固定材料测答案的忠实度，LLM 裁判打分 + 我人工校验过裁判和我的判断一致（抽 10 题人工复核过，一致了才敢让裁判批量跑）。负例集：专门放了 5 个库里没有答案的问题测拒答——防幻觉测的就是'该说不知道时说不说'。两段分开的意义：答错时我能归因是'书没翻对'（检索）还是'翻对了没答好'（生成）——不能归因的优化就是玄学。"

考察意图与踩坑点

  • 考察意图：RAG 人人都有，面试官必用深挖区分"跟教程做的"和"迭代优化过的"。每层追问的答案里都必须有你自己的数字——这是真做过唯一的铁证。
  • 踩坑点：差异化说"我用了最新的模型"（和你无关）；优化手段全堆上去说不出取舍；没有任何量化。
  • 一句话总结：差异化 = 每环有决策理由 + 优化有先后证据 + 评估分段归因 + 拒答有负例集——把"标准项目"讲出"个人判断"。

Q04 · 通用：怎么讲任何一个项目？（叙事框架 + 高频陷阱）

难度：★★★ ｜ 频率：极高（元技能）｜ 对应课件：无（方法论）

面试官（所有面试的开场）："挑一个你最熟悉的项目讲讲。"

第 1 层追问：叙事框架

有没有一套万能结构？

参考回答：六格结构，任何项目通用：

1. 背景与问题（1 句）：什么场景、什么痛点、为什么值得做
2. 选型与理由（1-2 句）：为什么这个方案而不是另一个（对照着说）
3. 架构（3 句）：核心组件 + 数据流向，画得出简图
4. 最难的一个问题（重点花时间）：现象 → 止血 → 根治 → 根因
5. 结果（必须有数字）：成功率/延迟/成本，测的方法也要说
6. 局限与下一步（1 句）：主动暴露，展示判断力

纪律：时长 1-3 分钟（面试官会追问，别把子弹一次打光）；技术决策必须有对照（"用了 LangGraph"是事实，"为什么不用裸循环"才是判断）；数字必须是自己测的。

第 2 层追问：高频深挖问题清单

面试官通常从哪些角度追？

参考回答：六连击，提前每个项目过一遍："为什么这么设计？"（考选型逻辑——用对照答法）；"最难的问题？"（考真实性——没有踩坑经历的项目是编的）；"数据怎么测的？"（考严谨——测试集多大、跑几次、谁打的分）；"如果重做会改什么？"（考反思——"没什么可改"是最差答案）；"规模上去了怎么办？"（考扩展性——量级×100 时先崩的是哪环）；"你负责哪部分？"（考协作真实性——团队项目要能说清边界）。每个问题都值得提前写好答案——现场即兴组织语言的质量远低于书面准备。

第 3 层追问：没做过大项目怎么补救？

转行学员没有生产级项目，怎么不露怯？

参考回答：三条策略。一，用课程实战项目的"工程完整度"换"生产规模"：你的 DeepResearch Agent 有闸门、有轨迹日志、有评测集——生产思维比生产规模更打动面试官（面试官知道初级工程师缺的是规模不是思维，规模入职就有了）。二，量化做到极致：没有百万用户，就测"20 题测试集 5 次重跑的成功率分布"——小数字的科学性胜过大数字的模糊。三，诚实划界："这是学习项目，没上过生产；但我按生产的标准做了闸门、评测和日志，也清楚它离生产还差权限层和监控"——坦白"没做过" + 证明"知道差什么" = 可信且可培养；冒充生产经历，一个追问就塌方，还会连累其他真实经历的可信度。

考察意图与踩坑点

  • 考察意图：项目叙事是转行求职者的核心竞争力——知识差距可以补，可信度塌了救不回。
  • 踩坑点：流水账式介绍（"我先装环境然后……"）；所有项目都"很顺利"（没有踩坑 = 没有深度）；冒充生产经历。
  • 一句话总结：六格叙事 + 六连击预演 + 数字自测——转行者的胜负手是把学习项目讲出生产思维。
