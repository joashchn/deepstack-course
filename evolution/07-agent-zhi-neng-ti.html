1. 演进脉络：Agent 思想的三次点燃

1.1 思想源头（2022.12）：ReAct 论文

2022 年 12 月，《ReAct: Synergizing Reasoning and Acting in Language Models》提出一个简单却深刻的洞见：把「推理（Reasoning）」和「行动（Acting）」交织在一起——模型边思考边行动，思考指导行动，行动结果（观察）反过来修正思考。

ReAct 把 Agent 循环形式化为：

思考（Thought）→ 行动（Action）→ 观察（Observation）→ 再思考 → …

这个「思考-行动-观察」循环，至今仍是绝大多数 Agent 系统的主循环骨架。论文同时展示了它优于纯推理（CoT）或纯行动（Act-only）的原因：推理让行动有方向，行动让推理有依据，二者互相纠偏。

1.2 大众点燃（2023）：ChatGPT Plugins 与 AutoGPT

2023 年 3 月，OpenAI 发布 ChatGPT Plugins：ChatGPT 可以调用外部工具——这是大众第一次看到「聊天机器人真的去执行操作」。随后 AutoGPT、BabyAGI 等自治 Agent 项目一夜爆火，人们开始尝试让 AI 自主完成多步骤任务。

这一波热潮很快退烧，原因是深刻的：自主循环放大了模型的不可靠——无人看管的循环会跑偏、死循环、烧钱。但它完成了重要的认知教育：「Agent 是趋势」成为共识，问题从「要不要」变成「怎么可靠地要」。

1.3 工程化成熟（2024-2026）：从玩具到系统

2024 年起，Agent 进入工程化阶段：

  • 框架成熟：LangGraph、OpenAI Agent SDK 等让 Agent 从「手写循环」变成「声明式编排」
  • 可靠性成为主题：人机回环、权限控制、容错重试、可观测性成为 Agent 系统的标配（第 12 章 Harness）
  • Agent 形态分化：单 Agent、多 Agent（第 08 章）、Workflow（固定流程）三者各司其职
  • 2026 年：Agent 已是企业 AI 应用的主流形态——从研究助理、客服坐席到自动化运维，无处不在

2. 核心概念：Agent 循环的解剖

一个最小 Agent 由三部分组成：

组件 作用 示例
LLM 决策中枢：思考 + 决定行动 GPT/Claude/Qwen 等
Tools 行动手段：模型可调用的函数 搜索、计算、数据库、API
循环 把思考-行动-观察串起来 ReAct 主循环 
┌──────────────────────────────────────────┐
│            目标：帮我调研竞品并出报告          │
└──────────────────┬───────────────────────┘
                   ▼
┌──────────────────────────────────────────┐
│ 思考：我需要先搜索竞品公开信息               │
│ 行动：search("竞品A 最新动态 2026")          │
│ 观察：返回 12 条搜索结果…                   │
│ 思考：信息够了，开始撰写报告，引用来源…        │
│ 行动：write_report(...)                    │
│ 观察：报告已保存                            │
│ 思考：任务完成，输出总结                     │
└──────────────────────────────────────────┘

工程上的三个关键设计点（详见深度章节）：

  1. 终止条件：什么时候算「干完了」？——必须有明确的终止判断（目标达成、超步数、人工确认），否则循环会失控
  2. 最大步数/预算：防死循环的第一道闸门
  3. 人在回路：关键步骤（支付、删除、发布）必须人工确认——自主不等于失控

3. 关键认知：Agent 的成与败

Agent 为什么是革命性的： 传统软件是「人指挥机器」——所有步骤人肉编排；Agent 是「人定目标、AI 编排」——把中间步骤交给循环自主完成。它能完成「无法预先穷举步骤」的任务，这是传统程序做不到的。

Agent 为什么经常翻车： 三个系统性原因——

  1. 错误累积：每一步的小误差在循环里滚雪球，越到后面越偏
  2. 上下文漂移：长循环中早期目标被遗忘（上下文工程要解决的，第 09 章）
  3. 工具不可靠：工具的返回格式、失败模式远超设计预期

结论：Agent 系统的难点从来不在「让循环跑起来」，而在「让循环可靠地停下来、不出错地完成任务」——这正是后面所有工程化章节（上下文工程、Skill、Harness）要解决的。

4. Agent vs Workflow：一个重要的区分

2026 年的工程共识是区分两种形态：

维度 Workflow（工作流） Agent
步骤 预先编排，固定执行 自主决策，动态演化
适合 流程确定、可预测 目标明确、路径不定
可靠性 高 中（需工程手段兜底）
示例 固定 RAG 流水线 自主研究助理

经验法则：能写成固定流程的，先写成 Workflow；路径确实不确定的，才用 Agent。 别让 Agent 做它不需要做的事——这是成本与可靠性的双重考量。

5. 现状与趋势（2026）

  • 推理模型驱动 Agent：带思维链的推理模型让「思考」质量质变，复杂工具编排能力显著提升
  • Agent 协议标准化：Agent 间通信（A2A 等）与工具接入（MCP）标准逐步落地
  • 从「单任务循环」到「长周期系统」：Agent 开始承担持续数天/数周的任务，可靠性工程（第 12 章）成为成败关键

6. ReAct 之外：Agent 的模式家族

ReAct（思考-行动-观察）是最广为人知的模式，但它不是唯一的。了解整个模式家族，才能根据任务选对骨架：

模式 核心思想 适合场景 代表
ReAct 边想边做，行动结果反哺思考 路径不确定、需要探索 本章主循环
Plan-and-Execute 先做计划，再逐步执行，计划可中途修订 目标明确、步骤多的长任务 经典规划式 Agent
Reflection 生成 → 自我评审 → 修订，循环至达标 写作、代码、内容质量敏感 Self-Refine
ReWOO 规划与执行分离，避免中间推理污染上下文 长任务、上下文敏感 上下文省 token
工具内置推理（Reasoning Tools） 把推理写进工具调用，适合推理模型 复杂数学/逻辑/代码题 2025-2026 推理模型范式

选型直觉：任务要探索 → ReAct；任务要规划 → Plan-and-Execute；任务要质量 → Reflection；任务要省上下文 → ReWOO；推理模型 → 工具内置推理。实际系统常混用——比如「Plan-and-Execute 的外壳 + 每步 ReAct 的内核」。
